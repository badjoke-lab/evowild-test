## 操作と実機での追試

ZIPを展開し、最上位の `README.txt` があるフォルダーで `python3 -m http.server 8000 --bind 0.0.0.0` を起動する。PCは `http://localhost:8000/`、Androidは同一Wi-Fiから `http://PCのLANアドレス:8000/` を開く。比較結果は `/evowild-test/ridge-performance/` で閲覧できる。

1. 「出走設定」で通常の18体混走か、Sのみ50体・100体を選び、「新しいレース」を押す。「S型表示」で従来モデル／ピクセルv4.1を走行中に変更できる。
2. RaceまたはFollowを選び、「実機計測」に端末・ブラウザを入力する。「スタートから96フレーム測定」が終わったらJSONを保存する。画面を縦・横に固定し、同一条件の両表示を交互に各3回以上測る。
3. 旧版と新版で同じ操作を行い、「保存したJSONを比較」にまとめて読み込む。編成・カメラ・実描画サイズ・AAが一致する行を比較する。新版のJSONには統合ビルド名も入る。長時間走行時の発熱による性能低下、接地と密集時の識別性も実機で確認する。

## 何に時間がかかったか

同じ7時点を診断ページで再生し、シミュレーション・順位、Sの走行距離／姿勢／LOD、カメラ、各描画のCPU提出、HUD・ミニマップを計時した。GPUは描画順のまま地面、その他のコース・背景、各形態、表面、スプライトを区間計測した。通常の深度テストとMSAAは各区間に含む。独立した影・深度プリパス・ポストプロセスは0回。CPUのGPU完了待ちは描画後の1画素同期読出しで別採取した。[CPU・GPUの全内訳](evidence/cpu-gpu.csv)

| 画面・表示・条件 | 地面GPU 前→後 ms | S表面GPU 前→後 ms | その他の主な負荷 |
| --- | ---: | ---: | --- |
| PC・ピクセル・通常18体Race | 35.2 → 13.2 | 10.2 → 2.6 | 改修後のP/E/A描画 26.7 ms |
| PC・ピクセル・S型100体Race | 31.7 → 9.0 | 113.3 → 89.8 | S表面の平均提出三角形 109,208 → 68,339、呼出し33.4回で同数 |
| PC・ピクセル・S型100体Follow | 29.5 → 8.7 | 126.7 → 107.4 | S表面の平均提出三角形 201,715 → 160,277 |
| スマホ幅・ピクセル・S型100体Race | 32.6 → 5.2 | 74.0 → 64.1 | 改修後のGPU完了待ち 66.7 ms |
| スマホ幅・ピクセル・S型100体Follow | 30.6 → 5.1 | 56.7 → 64.4 | 地面は短縮、S表面の単独計時は増加 |
| PC・従来・S型100体Race | 48.7 → 15.2 | 従来S 244.3 → 256.7 | 従来モデルの描画が支配的 |

PC・100体Raceの遅い3区間は250.1～333.3 ms。直前の同じフレームを再生すると、S表面67.2～92.4 ms、地面4.8～8.7 ms、シミュレーション全体0.4～0.8 ms、UIのJS 1.7～4.5 msで、方位素材のストリーミングは0件だった。Followの遅い3区間ではS表面94.7～142.7 ms。少なくとも表面だけで33.3 msの予算を超える。同期再計測と実RAFの差にはブラウザのキュー・合成・スケジューリングが含まれ、同一フレームのGPUタイマーとの差し引きで内訳を確定することはできない。[遅い区間の再生結果](evidence/slow-replay.csv)

別試行のChromiumトレースでは、PC・100体Followの最も長い5つのコールバック間隔は293～388 msだった。GPUプロセスのメインスレッドでスケジューラタスクが占めた区間は各293～388 ms、レンダラー側のスタイル・レイアウト・ペイントの合計は8～16 msだった。ソフトウェアGPU側の処理や待機が長い区間と重なっている。タスク内の実行と待機の比率はこのトレースからは分からない。[Chromiumの96区間](evidence/chrome-follow-100.csv)

地面は固定平面、固定材質、固定照明で、元のThree.jsの照明式は視線方向で決まる。同じ材質・ライトを使って視線方向の128×128のテーブルをロード時に生成し、元の平面で参照する。霧と深度は実際の画素で処理する。

S型表面は既存の姿勢・LOD・バッチ分けを使用する。各バッチの透視カメラ位置をローカル空間で囲み、接地補正の両端でも全個体から裏面と判定できる三角形だけを提出前に除く。残りの索引は元の順序に保つ。三角形内で一定になる元の面陰影を事前に計算し、頂点共有の衝突時は同座標の頂点に属性だけを分ける。縮退面と透視補間が不安定な向きは元の画素ごとの陰影式に戻す。ランタイムの索引キャッシュ上限は8 MiB。

100体の候補試験では、陰影を無条件に事前計算する方式がスマホ幅で最大228階調の局所差を生んだ。近い個体を先に提出する候補は同一深度の画素が変わり、深度プリパスの候補はGPU完了待ちが146.3 msに達した。これらは採用版から外した。候補表のプリパス行の表面GPU列は色パスのみ、完了待ち列は深度と色の両方を含む。[候補試験](evidence/candidates.csv)

## 画質と回帰

同一の168組（24条件×7時点、計71,391,516画素）で、全個体の位置・向き・走行状態・順位、カメラ、提出個体ID、Sの姿勢・LODが改修前後で一致。個体画像の前景マスク差は0画素。個体のRGB差は合計990画素で、いずれも最大1階調。地面を含む全画面も各チャンネルの差は最大1だった。PC・100体Raceの最初の比較時点では100体すべてが画角内で、内訳は近景13・中景62・LOD移行15・遠景10。この比較は、前後で頭冠・脚先・尾や接地表現が変化したかを検証するもので、元のv4.1に残る脚の重なりや足滑りの絶対評価は別途必要になる。

従来表示とピクセル表示を、Sのみ1・10・50・100体と通常18体混走で切り替えた。各7地点で全個体の状態が一致し、Tacticalは描画画素も一致した。Race／Follow／Tactical／Morph、停止・再開・リセットを通過。通常18体のSTARTからFINALまでに、57通りの順位列、ブロック、追越し、レーン変更を記録した。順位・スタミナ等のエンジン本体とカメラ軌道のソース照合も通過した。

通常ゲームの既存ブラウザテストも3件通過した。モバイル専用の撮影テストはPC側で対象外1件。[テスト出力](evidence/ordinary-race-tests.txt)

比較画像は実際のカメラで得たフレームを並べた。動画はS型50体・100体の1800mコースで実時間収録し、途中でRaceからFollowに切り替えている。白い胴体と頭冠が密集時に重なり、後方視点で四脚を個別に数えにくい問題は残る。

## 次の検証候補

同じ地面で旧S表面と今回の表面を差し替えた対照試験では、PC・100体Raceの表面GPUが108.5→89.8 ms。Followは109.3→107.4 msと小さく、スマホ幅Followは50.4→64.4 msだった。さらに診断時だけ表面色を定数にしても、同じ三角形・深度・ディザでPCのRaceは50.9 ms、Followは70.6 msを要した。色・陰影を求める経路には数十msの余地がある一方、定色描画でも予算を超える。[S表面の対照試験](evidence/surface-controls.csv)

次の候補は二つある。まず同じ姿勢の表面を小さな三角形群に分け、全体が視錐台外または確実に裏向きの群を頂点処理前に除外する。特に近距離のFollowで部分的にしか映らない個体について、提出三角形とGPU時間を測る。次に、三角形が参照し得る元ボクセルの色がすべて同一と証明できる面に限り、画素ごとの3D色参照を省く。どちらも今回の168組の輪郭・色差と96実RAFを再検証して判断する。

同じZIP・同じ画面条件を物理GPU搭載PCとAndroidで計測し、平均とp95が両方とも予算内に入ることを採用条件とする。実機では高負荷区間のGPU時間と画面の密集を照合し、SwiftShaderでの順位付けが実機にも当てはまるかを確認する。
