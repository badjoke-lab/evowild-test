# EvoWild Run — S型レース仮統合

**判定は仮統合済み・製品採用保留（REVISE）。** リポジトリの通常のゲーム入口から「S型レース試験」で1800m Ridge Ovalを開く。レース走行中や停止中にS型表示を切り替えられる。物理Android端末とGPU搭載PCの測定結果は未取得。

## デモと実機測定

1. ZIPを展開し、同梱の `README.txt` と同じフォルダーで `python3 -m http.server 8000 --bind 0.0.0.0` を実行する。PCは `http://localhost:8000/`、同じWi-Fi上のAndroid Chromeは `http://<PCのLANアドレス>:8000/` を開く。ビルド済みのためNode.jsは不要。
2. 「出走設定」で1・10・18・50・100体、通常混走またはSのみを選び「新しいレース」を押す。これは新しい出走。「S型表示」の変更は走行位置、時刻、選択個体、カメラを引き継ぐ。通常ゲームは従来表示の18体混走で起動する。
3. Race／Followで走行、Pause／Resume、Resetを操作できる。Tacticalでは既存のマーカー、Morphでは既存の標本を表示する。
4. 計測するカメラを選び、「実機計測」に端末名を入力し「スタートから96フレーム測定」を押す。コースの初期配置とカメラをリセットし、通常のレース更新に1/30秒ずつ渡す。24フレーム予熱後に96個の実際のRAF開始間隔を保存する。通常プレイは本体の可変時間ステップで動く。途中のPause・Reset・カメラ変更・タブ非表示・描画寸法変更で測定を中断する。
5. 「JSONを保存」。GPU搭載PCとPixel 7級Androidの各端末で、画面向き・ブラウザ・電源条件を記録し、50体・100体を両表示でそれぞれ3回以上、順序を交替して測る。「保存したJSONを比較」から後日まとめて読み込める。ファイルは端末内で処理する。
6. 比較画面はコース、編成、頭数、画角、カメラ、描画バッファ寸法、AA条件を区別する。同条件の最初の有効な記録を基準にFPSとp95の差を表示する。方位素材の読込を含む記録は確認用。従来のv4.1単体デモで保存した各48時点のJSONも読み込める。単体試験の同期読出しと統合レースのRAF間隔は別表で扱う。

## ゲーム本体との接続

| 項目 | 接続方法 |
| --- | --- |
| 個体制御・順位 | `src/main.js` の `update`、`gapAhead`、`laneFree`、`chooseLane`、`ranks` を両表示が共有する。ブロック、追越し、スタミナ、周回位置は既存の処理が決める。この本体の接触判定は同一レーン内の距離と進路の空きによる。 |
| コース・カメラ | 本体のCatmull–Romコース、Three.jsの透視カメラ、色・深度バッファを共用する。描画後にSだけを同じ深度面に送信する。既存メッシュで描くP/E/A、リング、環境、ミニマップ、順位表を維持する。 |
| Sの位置・走行・接地 | 本体の `r.obj.position` と `rotation.y` を読む。原本の前方向 −X をゲームの +X に合わせ、700原本単位を4.65本体単位×既存個体スケールに換算。前進移動量から24姿勢と支持脚のサブフレーム補正を選ぶ。地面は本体路面 y=0.03、足底基準は0.034。姿勢内の上下動は原本に含まれる。 |
| 近・遠景 | v4.1の表面クラス、17色ペイント、方位・深度スプライト、6×6グリッド、ディザを既存ファイルから読む。既存シェーダーの投影をゲームの行列に接続する。103–113pxの移行、148／245pxの段階はv4.1と同じ。方位のロード中は表面で描く。透視の近景では正投影用の方位別索引を使わず、既存の全表面索引とGPUの裏面カリングを用いる。 |
| 出走と負荷試験 | 通常の18体は同じ名前、色、形態、開始距離、選択#06。試験編成は同じ6レーンと開始間隔を頭数に展開する。1体時は#01を選ぶ。Sのみの編成では全員が既存のS型能力値で走る。 |

## 回帰・画質と性能

既存エンジンの順位・進路・更新コードは指定開始HEADと一致する。Sのみ1・10・50・100体と通常18体混走を同じブラウザ入力・時刻で比較し、各7地点で全個体の走行状態、脚の骨格角、順位、カメラが一致した。Tacticalの最終画素も両表示で一致した。18体でSTARTからFINALまで、ブロック、追越し、進路変更、順位変動を確認した。既存の `tests/race.spec.js` もデスクトップ・Android画面設定で3件通過した（モバイル専用テストのPC実行1件は対象外）。[回帰記録](evidence/regression.json)

同一個体をゲームのTactical→Race→Followカメラで追い、140フレームで頭冠・四脚・尾を確認した。近景は頭冠の分岐と尾が読める。背面に近いFollowでは脚と尾が重なり、遠景・密集時は隣の白いSとの境界が読みにくい。近景から遠景への比較資料には実際の角度・姿勢・投影幅を併記した。既存の単体試験の頭冠IoUは別の投影条件で測った値で、今回の画質指標には転用していない。[全フレーム](evidence/quality-frames.json) · [姿勢内の接地検算](evidence/quality.json)

## 採用条件と未解決問題

- 実機受入の目安を平均30fps以上、p95は1フレーム予算33.3ms以内とする。物理AndroidとGPU搭載PCで同じ編成・カメラを反復し、遅い回を含めて評価する。温まった端末での持続性能も未確認。
- 統合シーンではコース全体、既存の他形態、順位表・ミニマップも毎フレーム動く。今回の統合RAF計測はこれらを含む。単体試験のパス別GPU時間から、統合シーンで遅いフレームの原因は特定できない。
- 個体の色、奥行きの重なり、元の密な出走グリッドの影響で、遠景では頭冠・四脚・尾から1体ずつを見分けにくい。接地検算は同一姿勢内の支持脚の水平移動量を調べたもの。姿勢境界の接地、コーナーで重なる個体の見え方は実機でも確認する。
- PCはゲーム本体の標準AA設定、タッチ端末は本体のモバイル設定を引き継ぐ。端末間の画角・画素数・AAの差は比較時に記録する。
